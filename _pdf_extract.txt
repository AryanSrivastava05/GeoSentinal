Executive Summary
The GeoSentinel project proposes an AI-driven landslide early warning and safe-relocation system for
India’s North Eastern Region (NER). By integrating real-time environmental sensing, satellite imagery, and
historical data, the system will predict high-risk zones and issue alerts to authorities and communities.
Crucially, it extends beyond warning to facilitate safe relocation from vulnerable areas (the “wow” factor of
combining SIH26001 and SIH26191). 
We envision a staged development path: 
Prototype (Internal Hackathon): Rapid proof-of-concept with core ML model and simple GIS
dashboard. 
Pilot MVP: A functional regional system with real data ingestion (rainfall, soil moisture, DEM, etc.),
field reporting app, and localized alerts. 
Production: Scalable cloud deployment covering multiple districts, robust APIs, offline mode, and
integration with government workflows (e.g. IMD alerts). 
Key deliverables include risk heatmaps, a predictive analytics engine, and mobile/web apps for field data
and alerts. We will use official datasets (IMD, ISRO/NRSC, NASA) and open sources (WorldPop, OSM), and
technologies like Python, PostGIS, and Kubernetes. An AI model (e.g. XGBoost) will fuse features like recent
rainfall, soil moisture, slope, and landcover to produce probabilistic risk scores. Explainability (SHAP values)
will highlight drivers of risk. 
A demo plan covers historical back-testing (e.g. Kedarnath 2013), simulated sensor feeds, and field-test
scenarios. We recommend three pilot districts (Meghalaya’s West Khasi Hills, Assam’s Dima Hasao,
Nagaland’s Mon) based on high landslide incidence and data availability. A detailed timeline (Gantt chart)
and team plan support internal selection. 
This comprehensive report includes data sources, architecture diagrams, ML design, UI concepts, timelines,
and a submission checklist, with citations to authoritative sources. We aim to improve disaster
preparedness, reduce casualties, and enhance climate resilience in NER.

Stage 3: Production System
Objectives
Full Coverage: Extend system across NER states and scale to national-level infrastructure as needed.
Robust Backend: Containerized microservices (Docker/Kubernetes) with auto-scaling (AWS/GCP). 
Advanced Analytics: Integrate more ML/DL models (e.g. LSTM for time-series rainfall, deep
networks for image-based detection of cracks). 
Interoperability: Connect with national platforms (NDMA, IMD dashboards) via APIs. 
Emergency Operations Center (EOC) Mode: Real-time dashboards for district admins to dispatch
responders, plus push alerts to public via multi-channel (SMS, radio, local loudspeakers). 
Relocation Execution: Integrate carrying-capacity model (SIH26191) to plan evacuation bus
allocation, shelter assignments, and safe-route guidance. 
Deliverables
Scalable Cloud Deployment: Kubernetes cluster , managed DB (PostGIS/RDS), continuous
integration. 
Refined Predictive Engine: Ensemble of models (e.g. XGBoost + RandomForest + CNN on satellite
images) with performance evaluation. 
Full-featured Apps: Field apps with user accounts and richer UI (offline maps, manuals), public app
for alerts. 
Govt Integration: APIs feeding into District Warning Centers; dashboards with role-based access
(NDMA, SDRF, local). 
Evacuation Planner: Module that ranks villages by risk and suggests relocation capacity (integration
of population data【40†L15-L23】, terrain). 
Comprehensive Testing: Stress tests, security audits, disaster drills with emergency services. 
Scope & Limits
Region: All of NER (and potentially replicate in other hilly regions). 
Data: Full historical archives (NRSC landslide atlas【30†L8-L16】 of 80k events), continuous satellite
feeds, dense station networks. 
Team: Full project team (~10–12) including DevOps, data scientists, GIS specialists, and liaisons with
government bodies. 
Limitations: While real-time hazard monitoring is robust, no guarantee of preventing all disasters. It
augments, not replaces, engineering solutions (e.g. slope stabilization). 
Milestones & Effort
Enterprise Architecture (50 PD): Design high-availability system; set up cloud infra (compute, data
lakes, GIS server). 
Model Ensemble & Tuning (40 PD): Train advanced models, tune via cross-validation on long
historical records. Incorporate explainability (SHAP) for transparency. 
API & Integration (30 PD): Secure APIs for two-way data exchange (weather forecasts, landslide
reports); integration with IMD feeds and National Open Data initiatives. 
User Interfaces (40 PD): Polish apps/UI, conduct user training manuals in local languages.

Risks & Mitigations
Scaling Issues: Handling big data and many users. Mitigate: Use serverless (Lambda) for bursty

False Alarms: Over-warnings could lead to complacency. Mitigate: Calibrate alerts to balance false

Privacy & Data Sensitivity: Citizen data (e.g. location reports) must be secured. Mitigate: Follow IT

Maintenance: System upkeep after launch. Mitigate: Train local IT staff; document code; use
managed services for easier support.
Acceptance Criteria
Reliability: 24×7 operation with automated failover; <99.9% uptime during monsoon season. 
Performance: System handles daily forecasts and sensor feeds with <1-hour latency; apps sync
updates within minutes of connectivity. 
Accuracy: Empirically validated model (e.g. AUC > 0.8 on test set, sufficient recall on historical
events). 
Usability: Local officials and community users can operate apps and dashboards with minimal
training (assessed via user feedback). 
Impact: Demonstrated reduction in response time or better evacuation outcomes in drills
(compared to pre-system baseline).

Technology Stack & Architecture
The system will evolve over stages, but core technologies include:
Programming & Frameworks: Python (data processing, ML with scikit-learn/XGBoost/TensorFlow),
R (if needed), Node.js or Django/Flask for backend APIs, React or Vue for frontend, React Native/
Flutter for mobile app. 
Data & DB: PostgreSQL with PostGIS extension for spatial data; time-series DB (InfluxDB) for sensor
logs; object storage (AWS S3 or GCP Buckets) for large raster (DEM, imagery).

Cloud Infrastructure: Initially local development; pilot on AWS/GCP VMs; production on Kubernetes
(EKS/GKE) with auto-scaling. Serverless (AWS Lambda) for on-demand processing (e.g. ingest API,
SMS gateway). 
GIS/Mapping: GeoPandas, GDAL for preprocessing; Leaflet or Mapbox GL JS for web GIS; QGIS for

Machine Learning: Python ML libraries (scikit-learn, XGBoost, LightGBM), possibly TensorFlow/Keras

PySAL) if needed. 
Mobile/Offline: App with local storage (SQLite or PouchDB) to cache data and reports; sync logic to
handle intermittent connectivity. Use of SMS gateway APIs (Twilio/MSG91) for broadcast alerts. 
APIs & Integration: IMD open-weather APIs【28†L37-L42】 for forecasts; NASA/Google APIs for
global datasets (GPM); Government open data portals. RESTful JSON APIs for all internal data flows. 
DevOps: GitHub/GitLab CI-CD, Docker for containerization, Prometheus+Grafana for monitoring, ELK
stack for logs (optional). Use VPN or secure channels for sensitive data.

Model Choice & Training
We will build a supervised model to predict landslide risk score (continuous) or binary landslide/no-landslide
for upcoming period. Likely candidates include Gradient Boosting (XGBoost/LightGBM) and Random
Forests, which handle heterogeneous features and provide feature importance. We will also explore deep
learning (e.g. CNNs on satellite images) if warranted. Hyperparameters (learning rate, depth, etc.) will be
tuned via cross-validation; a baseline might be XGBoost with 100 trees, max depth 6. 
For regression, we may predict slide probability or expected volume; for classification, we output risk
categories. Baseline metrics to track: ROC-AUC, Precision/Recall, F1-score, and calibration (to avoid
overconfidence). If data imbalance exists (few landslides vs many non-events), we’ll use sampling or class
weighting. 
Evaluation Metrics
Accuracy / AUC: Overall detection accuracy and AUC (receiver operating characteristic) for true/false
positives. 
Recall at fixed FP rate: e.g. recall of actual landslides at 10% false-alarm rate. 
Precision/False Alarms: Low false-positive rate is crucial to avoid warning fatigue. 
Lead Time: How many hours before event is a warning triggered (on historical cases). 
Confusion Matrix: On held-out events, to quantify missed incidents vs false alerts. 
Explainability (SHAP)
We will compute SHAP (SHapley Additive exPlanations) values to interpret model outputs. SHAP can show,
e.g., that “high 7-day rainfall and steep slope” contributed strongly to a high-risk score at a location. This
transparency helps officials trust the model. We will analyze SHAP importance across the region to ensure
the model aligns with domain knowledge (e.g. heavy rainfall should increase risk) and to detect any biases.
Demonstration Plan
To validate and showcase GeoSentinel, we will:
Historical Replay: Re-run the system on past disaster events. For instance, simulate the 2013
Kedarnath landslide by feeding historical rain data; our model should have flagged that valley (it
has been identified as very susceptible【69†L364-L372】). We’ll generate an animation or sequence
showing predicted risk rising days before the event, and map overlays of actual slides for
comparison. 
Simulated Sensors: Connect simulated rainfall/soil sensors to the pipeline. For example, feed
recorded hourly rain from an IMD station into the model in “live” mode to trigger an alert scenario.
This tests real-time integration. 
Test Cases: Evaluate edge cases (e.g. high rain in flat area → no false alert, vs moderate rain on
steep slope → alert). Include unit tests for each module (data ingestion, model inference).

8. Phase 4 — GIS Relocation Engine
After a village becomes critical, the system must answer: where can people go?
Hard filters
 Reject sites inside critical landslide/hazard zones.
 Reject sites inside the chosen flood exclusion layer.
 Reject sites beyond the chosen slope limit.
 Reject sites without usable road access.
 Reject sites with insufficient usable area.
Suitability score
 score = 0.30 × safety + 0.25 × road_access + 0.20 × usable_area + 0.15 × distance + 0.10 × infrastructure
These weights are prototype assumptions, not universal planning standards. Store them in a configuration file so
they can be changed without rewriting the algorithm.
Return the top three sites with score, capacity, distance, access and the reason each site passed the filters.

Identify villages whose risk exceeds the critical threshold, then sum their population.

 capacity_people = floor(usable_area_m2 / area_per_person_m2)

Hackathon problem statements: SIH26001 (early warning for landslide-prone zones in NER) and SIH26191

2. Problem Statement
India's North Eastern Region receives among the highest annual rainfall in the world. The combination of
steep terrain, clay-heavy soils, deforestation, and intense monsoon events makes NER one of the country's
most landslide-prone regions. Existing warning systems — where they exist at all — issue generic
district-level alerts with insufficient lead time and no actionable relocation guidance.
2.1 Core Pain Points
 No village-level granularity: Alerts cover entire districts; high-risk villages cannot be distinguished from
safe ones.
 Warning without action: Even when alerts are issued, authorities have no systematic tool to decide
where people should go.
 Capacity blindness: Relocation sites are chosen ad-hoc, frequently overloaded, or accessible only
through hazard zones.
 Language barriers: Alerts in English or Hindi do not reach communities speaking Khasi, Dimasa, or
Nagamese.
 Connectivity gaps: Remote valleys lose internet during the most critical storm events, making cloud-only
systems unreliable.

To become the authoritative decision-support layer for landslide disaster management in North Eastern India —

 Not validated for operational use — prototype thresholds and weights are assumptions pending
calibration.

6. Functional Requirements
6.1 ML Risk Model (Step 3 — Friend's Scope)
Documented here as a contract your GIS/API work depends on.
 FR-ML-01: Accept features [slope_deg, rainfall_7d_mm, elevation_m, soil_code, history_density] per
village.
 FR-ML-02: Output a continuous risk_score ∈ [0, 1] for each village.
 FR-ML-03: Classify villages as LOW (< 0.4), MEDIUM (0.4–0.7), or CRITICAL (> 0.7). Threshold must be
configurable.
 FR-ML-04: Report precision, recall, F1-score, and ROC-AUC on a held-out test set.
 FR-ML-05: Save model and preprocessing pipeline together as a single joblib artifact.
 FR-ML-06: Provide SHAP feature-importance values for any single prediction on request.
 FR-ML-07: Prevent data leakage — use time/geographic splits, not random row splits.
6.2 GIS Relocation Engine (Step 4 — Your Scope)
 FR-GIS-01: Accept a list of CRITICAL villages (risk_score > threshold) with population and geometry.
 FR-GIS-02: Load candidate_sites.geojson. Apply hard filters — reject any site that: (a) overlaps a
landslide/hazard zone, (b) overlaps a flood-exclusion zone, (c) has slope_deg above the configured limit,
(d) has no road access, (e) has usable_area_m2 below minimum.
 FR-GIS-03: Score remaining sites: 0.30×safety + 0.25×road_access + 0.20×usable_area + 0.15×distance
+ 0.10×infrastructure. Weights must be configurable via a config file.
 FR-GIS-04: Return the top 3 sites per critical village, each with: site_id, score, capacity_people,
distance_km, access_road, filter_reason.
 FR-GIS-05: All distance calculations must use a projected CRS (not WGS84 degrees).
 FR-GIS-06: Output must be deterministic for the same input.
6.3 Population & Capacity Allocation (Step 5 — Your Scope)
 FR-CAP-01: Capacity formula: capacity_people = floor(usable_area_m2 / area_per_person_m2). Default
25 m²/person — configurable.
 FR-CAP-02: Sum affected population across all CRITICAL villages.
 FR-CAP-03: Allocate to ranked sites in order; never assign more than site capacity.
 FR-CAP-04: Explicitly report any unallocated remainder — never silently drop people.
 FR-CAP-05: Allocation must be idempotent — same inputs always produce same outputs.

15. Glossary & References
15.1 Key Terms
 DEM: Digital Elevation Model — raster grid of terrain heights.
 CRS: Coordinate Reference System — projection used for geospatial data.
 XGBoost: Extreme Gradient Boosting — ensemble ML algorithm used for risk classification.
 SHAP: SHapley Additive exPlanations — method for explaining individual ML predictions.
 ROC-AUC: Area Under the Receiver Operating Characteristic Curve — primary model evaluation metric.
 GeoJSON: Open standard JSON format for encoding geographic data structures.
 Hard Filter: A site exclusion rule with no override — site is rejected if condition is true.
 Suitability Score: Weighted composite score (0–1) ranking candidate relocation sites.
 NER: North Eastern Region of India (Assam, Meghalaya, Nagaland, Manipur, Mizoram, Tripura,
Arunachal Pradesh, Sikkim).
 SDRF / NDRF: State / National Disaster Response Force.
